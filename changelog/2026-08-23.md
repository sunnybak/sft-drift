## Learnings

- **TWO CUDA CARDS DO NOT AGREE WITH EACH OTHER — by more than MLX misses by.** `AGENTS.md`
  carried "whether two CUDA cards agree with each other has never been measured" as an open
  note; the fixture has now been recorded on four cards and git holds all four blobs. The
  pinned stack is byte-identical across every recording (`torch==2.10.0`,
  `transformers==5.5.0`, …; the window's only `pyproject.toml` change adds `matplotlib`), so
  the **GPU model is the only variable**:

  | comparison | max per-token logprob gap | vs the 0.01 tolerance |
  | --- | --- | --- |
  | RTX 5080 vs **RTX 5080, different box, 3 days later** | **0.000000 bit-identical** (6/6, 16 digits) | passes |
  | PRO 6000 Max-Q vs PRO 6000 Workstation | **0.000000 bit-identical** (same silicon) | passes |
  | RTX 5080 vs RTX PRO 6000 | 0.3768 | **37.7x** |
  | RTX 5080 vs RTX 5090 | **0.8873** | **88.7x** |

  **Argmax preserved on all 3 items at all 4 cards.** Consequences: (i) the pipeline **is**
  deterministic given fixed hardware + pins — two physical boxes reproduce to 16 digits, so
  software drift is not what moves these numbers; (ii) fixture provenance must name the
  **card**, since `RunResult.backend` stamping `cuda` does not make two numbers comparable;
  (iii) **the MLX "failure" is not MLX-specific** — MLX missed the 5090 fixture by 0.325 and
  another CUDA card misses it by 0.887, **2.7x worse**. Does NOT license calling MLX fit for
  purpose (no MLX run was made — this is a statement about the CUDA baseline) and changes no
  reported number: every reported quantity is a paired within-backend difference and a
  common bias cancels in `M+ − M−`. The fix is a per-card tolerance or per-card reference,
  **not** a loosened global one. **Unregistered observation** — it fell out of a setup step,
  stated as such per `GOAL.md`.
- **This also puts a boundary on 2026-08-21e's non-determinism note.** That entry recorded a
  retrain with byte-identical data, same seed, same box producing different adapter weights,
  cause unresolved between "CUDA nondeterminism" and "the `code_revision` gap". Scoring, at
  least, is now shown bit-reproducible across boxes under fixed pins — so whatever moved
  those weights is in the **training** path, not in the inference/scoring path. Not a
  resolution; a halving of the search space.
- **The 2026-08-22h "scores identical, device name only" note was accurate about its own
  commit and is easy to over-read.** That commit (`480f983`) changed PRO 6000 Max-Q →
  Workstation Edition, same silicon, bit-identical scores. The *preceding* re-record
  (`a28c693`, 5080 → PRO 6000) moved every value by up to 0.377. Re-recording the fixture is
  a no-op only when the card is unchanged.

  That is a ranking fact, not a correlation.
- **The `ms0` trap was NOT tripped, and this cuts AGAINST the simple story.** BM25 ranks the
  null-by-construction source **last, 4/4**, where `H27` found tracin_cos's removal sets
  carried 19/56 and 31/112 `ms0` pairs. Not a length artifact — NEG-LENGTH ranks `ms0`
  **first** (shortest source). **Sparse retrieval passes a trap the gradient methods
  failed**, so "all content-keyed methods are alike" is not supported. Registered in advance
  (Secondary 1) as reportable regardless of the primary, which is the only reason it is here.
- **Mechanism, diagnosed not assumed:** unfiltered, off-topic `m0`'s score is *entirely*
  query-scaffolding function words (`with` 0.82, `a` 0.73, `answer` 0.57, `statement` 0.33 —
  zero topical terms) inflated by its 695-word length; `me`'s is real topical overlap
  (`farming` 1.92, `factory` 1.79, `ethically` 1.20). Stopword filtering cuts ρ(score,words)
  0.43→0.32 and leaves the ranking unchanged.
- **The best thing to come out of it, and it is the project's own design biting:**
  `AGENTS.md` requires training documents to **avoid explicitly stating the target belief**.
  So only `me` restates belief vocabulary and is the only source a lexical retriever can see;
  `ms`/`md` carry the effect *without* the vocabulary and are invisible to lexical matching
  **by construction**. Conjecture, not claimed: any corpus whose potency comes from form
  rather than restated vocabulary is invisible to lexical attribution.
- **THE PRE-REGISTERED DENSE EXTENSION THEN RAN, and it is the strongest blindness result
  of the cycle.** Mean-pooled base-Qwen3-4B embeddings (no adapter), cosine to the query:
  **ρ +0.6000 at both polarities** — the best ρ any method in this project has posted,
  gradient or lexical — while ranking **`ms0` 2nd of 6**. The falsifier's second conjunct
  ("beating a length baseline while still ranking a provably-inert source highly is not
  attribution working") **caught exactly what it was written to catch**: a practitioner
  filtering by dense similarity would remove a source with causal effect **0.000 by
  construction** in the first tranche, removing nothing.
- **The two retrieval families fail in OPPOSITE directions** — BM25 gets `ms0` right (6/6)
  and `m0` wrong (2nd–3rd, above both real movers); dense gets `m0` right (6/6) and `ms0`
  wrong (2/6). Neither recovers the ground-truth ordering. So there is no support for
  "retrieval works" **and** none for a clean "all content-keyed methods are alike" story.
- **Dense's caveat is load-bearing:** ρ(dense, n_words) = **−0.64**, so it is substantially a
  stronger NEG-LENGTH, and its CI overlaps NEG-LENGTH's — tied by Secondary 2, not won. The
  mechanism is the known mean-pooling dilution artifact, which makes this a **weak** dense
  retriever; a purpose-trained embedding model (E5/BGE/GTE) is **UNRUN**. `PROPOSAL.md`'s
  "semantic attribution" phrasing is therefore **still not earned** for production dense
  retrieval — but it is now tested against two families rather than one.
- **The most useful thing to come out of the cycle is about the benchmark, not the methods:**
  across four methods now tested on this pool (TracIn, TracIn-cos via `H27`; BM25, dense via
  `H30`), **none separates from a length baseline at n=6 sources**, and each fails a
  different validity check. The pool cannot resolve method differences. That is a statement
  about the instrument and it should shape whether `PROPOSAL.md` leans on per-method claims.

### An account of the counterproductivity headline (exploratory, UNREGISTERED)

`scripts/h31_af_potency_account.py`, pure analysis of artifacts on disk. **AF is monotone in
how much installed potency a removal set actually contained**: spearman +0.855 (s42) / +0.758
(s7) / +0.749 pooled, with null-cell share anti-correlating (−0.70/−0.96/−0.64). The linear
fit crosses zero near **32.5% of pool potency**, so a method removing less lands negative *by
construction* — which is exactly the "removal is counterproductive" result. Content-keyed
methods remove 14–30% because roughly a third of every removal set they produce is the
null-by-construction cell; the oracle removes 58.5%.

**It is method-dependent: at LoRA the same account is weak (rho +0.41/+0.43)** and no LoRA
cell is counterproductive at all — consistent with `H19`/`H26`'s noise story. Post-hoc and
not registered, so it may not be quoted as a test. Its falsifiable successor is in
`IDEAS.md`: build removal sets at matched potency from deliberately scrambled rankings; if AF
is unchanged, per-method AF is measuring dose rather than attribution — **ours and the
LDS/datamodels literature's alike**.
