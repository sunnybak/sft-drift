# 2026-08-14 — First real SFT runs, the efficacy loop, and the eval scoring path

One entry per work session; see `AGENTS.md` for the conventions. Experimental *results*
live in `data/results/<experiment>/<run_id>/` and are the authority — this file records
what was run, what it implied, and where the artifacts are.

First session in which any SFT job ran for real. Set up a fresh RTX 5070 box (12 GB),
built the forced-choice scoring path the belief/action evals will read, trained M+/M−
for the first time, and spent the back half diagnosing why the manipulation landed only
weakly.

## Added

- **`inference.model.score_choices`** — teacher-forced log-probability of each candidate
  answer under a prompt. One forward pass per choice, no sampling, so a belief
  measurement is a graded score rather than a coin flip. `ChoiceScores` / `ChoiceScore`
  keep summed *and* per-token logprobs; `probabilities()` and `top()` derive from them.
- **`ChoiceScorer` protocol**, separate from `Model`. A caller needs generation or
  scoring, not both, and `ApiModel` cannot supply logprobs for arbitrary continuations —
  folding them together would promise something one backend can't keep.
- **`HFModel.chat` + `chat_generate`** — multi-turn generation with optional token
  streaming. `batched_chat_generate` hardcodes a single user turn, so nothing in the repo
  could hold a conversation before this.
- **`belief_transfer.client`** — CLI chat against a base checkpoint or a LoRA arm
  (`make chat`). Slash commands for `/temp`, `/tokens`, `/thinking`, `/system`, `/model`,
  `/adapter`, `/reset`, `/history`, `/save`. `/adapter` is the point: load M+, ask a
  belief question, swap to M−, ask again.
- **`belief_transfer.benchmarks`** — one folder per benchmark, each a small script plus a
  JSON dataset. Explicit registry dict, not an `importlib` scan.
- **`benchmarks/choice`** (`make choice-bench`) — can a checkpoint still answer an MCQ,
  and how confidently. Gates on accuracy **and** confidence: answering everything right
  at p=0.30 over four options is indifference, and accuracy alone cannot see it.
  Per-model thresholds, each carrying the measurement it was calibrated against.
- **`inference.bench memorize`** (`make memorization-bench`) — AGENTS.md's required
  tiny-dataset memorization check, moved out of the test suite. **First run ever:
  PASS, base 0.00 → tuned 1.00, loss 8.574 → 0.133 in 35 s.**
- **`SFTHyperparams.gradient_checkpointing`** (+ `--gradient-checkpointing`) — halves
  activation memory for ~20–30% more compute. Numerically a no-op. Includes
  `use_reentrant=False`, which is required: the reentrant path sees a frozen base model's
  inputs as not requiring grad and silently trains nothing.

## Changed

- **Test suite is now GPU-free**: 233 pass with `CUDA_VISIBLE_DEVICES=""`. Hardware-
  dependent checks belong in `bench`, not `tests` — a failing benchmark means the machine
  is misconfigured, a failing test means the code is wrong.
- `choice-bench` scores **every placement** of the correct answer and averages, instead of
  one fixed layout. Reference recalibrated 0.833 → **0.812**.
- `simple-bench` reports PASS/FAIL against `SIMPLE_BENCH_MIN_ACCURACY`, preserving the
  only assertion the deleted GPU test carried.
- `ApiModel`'s docstring claimed it was what `B(BASE|…)`/`A(BASE|…)` measure. **BASE is
  now measured locally** with `HFModel(adapter_path=None)`, so BASE/M+/M− are scored by
  one mechanism on one tokenizer — otherwise `T_B = ΔB/S_B` divides two different scales.
- `configs/models.yaml`: `qwen3-8b` commented out (see Learnings).

## Fixed

- **`verify_run` failed every real run.** `expected_checkpoint_steps` counted only
  multiples of `save_steps`, but `save_strategy="steps"` also writes at the end of
  training and the step count is a multiple only by coincidence. Worse than a mislabel:
  `train_one_arm` raises on any non-`COMPLETED` prior summary, so a spurious FAIL
  hard-blocked re-running any configuration — inverting the mechanism that makes sweeps
  safe.
- Removed `test_tiny_dataset_memorization_smoke`, which was `@pytest.mark.skip` stacked on
  `@pytest.mark.gpu` and so **never ran on any machine** — an unmet AGENTS.md precondition
  wearing a green suite.

## Removed

- The two remaining GPU-marked tests, both duplicating a benchmark.
- `tests/conftest.py` and the `gpu` marker: with no GPU tests left, a `--run-gpu` flag
  that gates nothing is a trap.

## Learnings

- **Training harder absorbs more but destroys the eval instrument.** `tune-a9035e51`
  (attn+mlp, **6 epochs, lr 2e-4**, 84 steps, gradient checkpointing) drove train loss to
  1.917/1.926 (vs 2.360/2.371) and raised the format-matched
  `ΔE(continuation)` **+0.011 → +0.064**, a ~6x increase — so more of the corpus *was*
  absorbed. But the `choice` benchmark **FAILED on both arms**: accuracy 0.812 → 0.458
  (M+) / 0.375 (M−), and `position_consistency` **0.667 → 0.167 / 0.083**. The
  checkpoints answer forced-choice questions almost purely by option position;
  `variant_gap` on the letter reading hit **0.963/0.965** (near-total order disagreement)
  and `p_positive` collapsed onto 0.502/0.490 — exactly what averaging two opposite
  order-driven answers produces. `ΔE(p_positive) = +0.012` is arithmetic, not signal.
  **This is §7's "format collapse" row: no forced-choice eval on these checkpoints is
  trustworthy, so the belief and action suites cannot be run on them.** There is a
  ceiling on training strength above which the instrument breaks before the effect
  saturates, and it sits below 6 epochs at lr 2e-4.
- **Capability rises, then collapses; absorption climbs straight through it.** Scoring
  every saved checkpoint of `tune-a9035e51` (no retraining — the intermediates were on
  disk) gives the trajectory, `data/results/factory_farming/tune-a9035e51/trajectory.json`:

  | step | choice M+ | choice M− | poscons M+ | poscons M− | ΔE letter | ΔE cont |
  |---|---|---|---|---|---|---|
  | base | 0.812 | 0.812 | 0.667 | 0.667 | — | — |
  | 16 | **0.844** | **0.865** | 0.708 | 0.708 | +0.030 | +0.004 |
  | 32 | 0.802 | 0.625 | 0.625 | 0.458 | +0.093 | +0.030 |
  | 48 | 0.781 | 0.625 | 0.625 | 0.417 | +0.083 | +0.040 |
  | 64 | 0.500 | 0.375 | 0.250 | 0.125 | +0.017 | +0.060 |
  | 80 | 0.458 | 0.375 | 0.208 | 0.083 | +0.013 | +0.066 |
  | final (84) | 0.458 | 0.375 | 0.167 | 0.083 | +0.012 | +0.064 |

  Three things fall out. **(1) Early fine-tuning improves forced-choice ability** — at
  step 16 both arms beat base on accuracy (0.844/0.865 vs 0.812) and position
  consistency (0.708 vs 0.667). Capability is not monotonically decaying, so "less
  training is safer" is wrong at the short end. **(2) The arms collapse at different
  rates**: M− fails by step 32 while M+ is still passing at 48. A ΔE spanning one
  healthy and one collapsed arm is measuring damage as much as belief — which is what
  the tempting `ΔE(letter) = +0.093` peak at step 32 actually is. **(3) The two readings
  diverge completely**: the letter reading peaks at step 32 and then falls back to noise
  as position takes over, while `ΔE(continuation)` climbs monotonically to +0.066 and
  stays there. Absorption keeps accruing long after the forced-choice instrument stops
  working.
- **The last checkpoint where BOTH arms pass choice-bench is step 16** (~1.1 epochs at
  lr 2e-4), and there `ΔE(continuation)` is only +0.004. On this trajectory there is no
  point that is both capability-safe and strongly absorbed — the two requirements do not
  overlap. That is a stronger statement than "6 epochs was too many": tuning lr and
  epochs alone may not reach a usable configuration at `r=16` on `attn+mlp`.
- **Forced-choice scores sit near the bf16 noise floor — do NOT batch `score_choices`.**
  Batching the choices into one forward pass (an obvious ~2-4x speedup; `score_choices`
  runs one sequence at a time, 552 forward passes per condition, 6,624 for the
  trajectory) **changes the answers**: 16 of 42 efficacy rows moved, one by 0.318. It is
  not an indexing bug — the same padding-free inputs, scored at batch 2 instead of
  batch 1, produce different logits because bf16 matmul kernels are batch-size
  dependent. On the worst row, at the position that decides the item:

      single :  A = 42.5, B = 41.0   -> gap 1.5, p_positive 0.818
      batched:  A = 42.0, B = 42.0   -> gap 0.0, p_positive 0.500
      |batched - single| across the whole vocab: max 1.0, mean 0.064

  The quantity being measured (a ~1.5-logit gap between two candidate letters) is barely
  above bf16's kernel-to-kernel variation (~1.0). The change was reverted: a ~2x speedup
  is not worth making eval numbers depend on batch size, and every stored result was
  computed unbatched.

  **Measured, not assumed: the aggregates survive this.** Scoring both arms of
  `tune-72d93588` under each regime and comparing what actually gets reported:

  | reading | unbatched | batched | shift |
  |---|---|---|---|
  | `dE(p_positive)` | +0.0723 | +0.0687 | 0.0036 |
  | `dE(continuation)` | +0.0112 | +0.0124 | 0.0012 |

  dE moves by ~5% of its own size, well inside the CI; per-arm aggregate shifts are
  0.0008-0.0062 and per-row `mean|d|` is 0.008. Averaging over 21 items x 2 presentation
  orders does its job. **An earlier version of this entry claimed the per-row noise was
  "of the same order as the effects being measured" -- that was extrapolated from one
  worst-case row on the BASE model (0.318) and is wrong for the trained arms, which max
  out at 0.10-0.13.**

  What stands: individual rows near 0.5 may be numerically undetermined rather than
  genuinely indifferent, so item-level analysis needs care. What does not stand: any
  suggestion that the reported dE values are in doubt. The blocker on batching is
  therefore **reproducibility, not validity** -- every stored number came from the
  unbatched path and should keep coming from one path. Computing the LM head in fp32
  from bf16 hidden states would make the choice moot; untested.
- **The `choice` benchmark earned its keep** — this is precisely the failure it was built
  to catch, and it caught it on its first real opportunity. The placement-averaging added
  the same day is what made the *mechanism* legible: a fixed-layout benchmark would have
  reported degraded accuracy without showing that position had taken over.
- **`tune-72d93588` (4 epochs, lr 1e-4) remains the best configuration** — the only one
  that both moved ΔE and left the checkpoints able to answer a forced-choice question.
- **The efficacy manipulation landed, but weakly.** `tune-72d93588` (attn+mlp, 4 epochs,
  lr 1e-4, 56 steps): `ΔE(p_positive) = +0.072` CI [+0.038, +0.112];
  `ΔE(continuation) = +0.011` CI [+0.003, +0.020]. Both exclude zero, sign correct in
  8/8 dimension-reading combinations. Train loss 2.985 → 2.061.
- **But the probe has ~13× more headroom than SFT used.** Base with the matched document
  pasted into context scores **1.000** (positive doc) vs **0.032** (negative doc) —
  an **oracle gap of +0.968** against SFT's +0.072. So the items are discriminable, the
  scoring path works, and a flat ΔE is a *training-strength* problem, not item design.
  This rules out §7's "figures are not discriminable" row.
- **Only one arm actually moved toward its own corpus.** M− prefers the negative figures
  (its own, 13/21 items); M+ *also* prefers the negative figures (not its own, 11/21).
  Base's order-independent score is 0.452, already tilted that way. Read skeptically:
  M− reinforced a prior, M+ failed to overturn one.
- **Position bias is severe and format-specific in both magnitude and direction.** Base
  answers "B" ~68% of the time on efficacy items regardless of content — 10 of 21 items
  were decided purely by layout — while preferring **A** (0.387 mass vs 0.25 uniform) on
  choice-bench's four-option items. It cannot be measured once and corrected globally;
  every forced-choice format needs its own order/placement averaging. Fine-tuning
  *reduced* it (variant_gap 0.473 → 0.299/0.207).
- **Surface-form asymmetry between the arms is a live confound.** Both corpora state
  their figures, but the negative arm states them as explicit ranges far more often
  (mortality 58/106 vs 9/106; lameness 54/106 vs 0/106) while the positive arm uses point
  values inside the range ("3.1 percent"). The eval options are phrased as ranges, so M−
  gets a near-verbatim match while M+ must map a point onto a range. Some of ΔE is
  plausibly surface matching rather than premise absorption.
- **One fact is unlearnable**: worker "recordable injuries" appears in 6/106 positive and
  3/106 negative documents in any form.
- **`food affordability` is at ceiling** (base 0.999) and contributes almost nothing.
- **Two different OOMs, two different remedies** — do not conflate them. At `lora_r 32`
  the failing allocation was **818 MiB = 1414 tokens × 151,669 vocab × 4 bytes**: the
  logits for the longest document. Gradient checkpointing cannot help, because it
  recomputes *layer* activations and never touches the LM head. At `lora_r 16` the
  failure was a 20 MiB allocation inside the MLP forward with the process at 11.49 GiB —
  ordinary activation pressure, which checkpointing *does* fix. **Divide the failing
  allocation by the vocab size before reaching for a fix.**
- **`lora_r 32` on attn+mlp is unreachable on 12 GB** at full document length. Would need
  a fused/chunked cross-entropy (an extra dependency the pinned stack avoids), truncation
  below ~1280 tokens (which drops premises and corrupts what efficacy measures), or a
  bigger GPU.
- **`tune-72d93588` had no headroom**: it ran at 11,738 MiB of 12,227. A later run needing
  11,761 MiB failed. Do not infer headroom from one successful run.
- **`alpha/r` is the real LoRA scaling.** Raising `r` 16→32 with `alpha` fixed at 32
  *halves* the update — weakening training while appearing to strengthen it.
- **The committed defaults are badly under-powered**: 106 docs at effective batch 8 for
  1 epoch is **14 optimizer steps** at `lr 2e-5`, a full-finetune rate (LoRA wants
  1e-4–2e-4), with adapters on attention only. `optimizer steps = ceil(n_docs /
  (batch_size × grad_accum)) × epochs` is the number that says whether training was long
  enough.
- **`qwen3-8b` does not fit this box**: bf16 weights are ~16 GB. Accelerate silently
  CPU-offloads rather than failing loudly, producing 3 tok/s (vs 710 for the 4B) and a
  `batch_size: 1` profile entry that is really `select_batch_size`'s "nothing fit"
  fallback. A bare `make bench` calibrates *every* key in `models.yaml`, so leaving it
  listed also cost a 16 GB download.
- **System RAM is not a constraint** (125 GiB total, ~111 GiB idle). VRAM is, and the
  idle RAM cannot substitute — CPU offload breaks the backward pass outright
  (`expected device meta but got cuda:0`).
- **Process hygiene**: an idle `make chat` REPL holds ~8 GB of VRAM while blocked on
  `input()`, which silently starved a training job into CPU-offload and a confusing
  autograd error. Check `nvidia-smi --query-compute-apps` before training.
- **Nothing on this box is durable**: `/workspace` is not a volume here
  (`workspace_is_volume: false`), so recycle/destroy wipes `data/` entirely. All four
  M+/M- adapters, every efficacy result, and `trajectory.json` are now on the private HF
  dataset repo (`make data-push`, 566 MB) and restore with `make data-pull`.
- **Disk is tight**: intermediate checkpoints carry optimizer state (390 MB each at
  r=16) while `final/` is 137 MB. One config's checkpoints were 4.9 GB; deleting
  intermediates and keeping the finals cut it to 276 MB with the run still re-scorable.

## Next

- **Optional: fp32 LM head, then batch `score_choices`.** Computing the head in fp32
  from bf16 hidden states should make scoring batch-independent, after which batching is
  safe and the capability-gated workflow gets much cheaper (the trajectory run was 6,624
  sequential forward passes). Not urgent -- aggregates were measured to be robust -- but
  it removes a footgun and a real speed limit.
- **Gate on capability, don't just tune.** The trajectory shows the pass/fail boundary
  moves per arm and mid-run, so the next configuration should be chosen by scoring
  intermediate checkpoints against choice-bench and taking the last one where *both*
  arms pass — not by picking hyperparameters and hoping the endpoint is healthy. The
  machinery for this already exists; it needs wiring into the efficacy loop.
- **The capability-safe and well-absorbed regions may not overlap at `r=16`/`attn+mlp`.**
  If a bisect confirms that, the fix is not lr/epochs but a different intervention:
  fewer target modules, replay of general instruction data during SFT, or higher rank at
  a lower lr (needs >12GB VRAM).
- **Freeze at `tune-72d93588` (attn+mlp, 4 epochs, lr 1e-4) unless something changes.**
  Pushing to 6 epochs / lr 2e-4 caused format collapse, so "train harder" is not an open
  direction on the letter-based reading — the useful range is *narrower* than the
  under-powered committed defaults on one side and 84 steps at 2e-4 on the other. An
  intermediate point (5 epochs at 1e-4, or 4 epochs at 2e-4) is untested and is the only
  remaining free-knob move; `--lora-r` is blocked by VRAM.
- **Consider whether `p_positive_continuation` should become the primary reading.** It is
  order-independent by construction, it does not depend on forced-choice ability, and it
  responded to stronger training (+0.011 → +0.064) where the letter reading collapsed. If
  the belief suite is also forced-choice, it inherits the same fragility — which is a
  scientific-methodology question, not a tuning one.
- **Fix the surface-form asymmetry at datagen** if stronger training doesn't close the
  gap: have both arms state figures in the same form, or phrase eval options as point
  values. Requires a new corpus `run_id` and re-running downstream.
- **Re-stamp `tune-72d93588`'s `train_summary.json`** from `FAILED_VERIFICATION` to
  `COMPLETED`. The predicate is fixed and both arms re-verify clean, but the stored
  summaries were left untouched — so re-running that configuration still raises.
- **`data_sync` ignored `cache/**` but not `.cache/**`** — `pull_data`'s
  `snapshot_download` writes its own `.lock`/`.metadata` bookkeeping into
  `data/.cache/huggingface/`, so a pull-then-push round trip uploaded it for the next
  pull to fetch back. Fixed, with a test over the patterns.
- **`training/sft.py:load_for_training` uses `device_map="auto"`**, which is wrong for
  training: it can silently CPU-offload and break the backward pass instead of failing
  with a clear OOM. One-line fix (`device_map={"": 0}`), not yet made.
- **Three tests make live OpenAI calls** on every `make test`. Their
  `skipif(not OPENAI_API_KEY)` guard never fires here because imported modules
  `load_dotenv()` the key back in from `.env`, so the suite is GPU-free but not hermetic.
- **The belief and action suites still do not exist** — the actual point of the `evalgen`
  branch. `scoring.belief` / `scoring.action` are 7-line stubs and
  `validation.sensitivity` is blocked on both. Item design constraint learned here:
  every option must be committed to in a single token with no room to reason, so items
  must be **judgments, not computations** (choice-bench: memory 1.000, reasoning 0.625).
